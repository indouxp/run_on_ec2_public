## 2. システム概要

### 2.1 目的
Amazon S3バケットへのアップロードイベントをトリガーとして、シェルスクリプトを自動実行し、その実行結果を適切な手段でユーザーに通知するシステムの構築を目的とします。本システムにより、ローカル環境のリソース制約を受けやすい高負荷処理を、クラウド環境の豊富な計算リソースで高速化できます。

### 2.2 システムの特徴
- **自動化**: ファイルアップロードによる自動実行
- **柔軟性**: 定義ファイルによる実行内容の制御
- **通知**: メール・SMS による処理結果通知
- **監視**: CloudWatch による実行状況の監視
- **セキュリティ**: IAM による適切なアクセス制御

### 2.3 システムの適用範囲
- 定期的なバッチ処理の自動化
- データ処理ワークフローの実行
- ファイル変換・加工処理

## 3. 機能要件

### 3.1 ファイルアップロード検知機能
**[001] S3イベント検知**

S3バケット（${BKT_IN}）への定義ファイル配置を検知します。

- 検知対象ファイル：*.conf（それ以外のファイルはスキップ）
- 検知をトリガーとして、Lambda関数（ts-010-lmd-010）を起動します
- Lambda の起動失敗・タイムアウト・異常終了時は、AWS が自動的に CloudWatch にエラーログを記録します

### 3.2 定義ファイル処理機能
**[002] 定義ファイル解析**

JSON形式の定義ファイルを解析します。

- 必須項目：prj_prefix, exec, log, result, mail, sms, ec2_role_name, subnet_name, sg_name, ec2_instance_name_tag, output_bucket, ses_from_email
- オプション項目：key_name, instance_type, ebs_size, ebs_type, timeout, default_ami_id
- 解析エラー時は CloudWatch にエラーログを記録します（通知先アドレスが取得できないため、メール・SMS 通知は行われません）

**[003] 定義ファイル検証**

各項目の形式チェックを実行します。

- `mail` のメールアドレス形式検証
- `ses_from_email` のメールアドレス形式検証
- `sms` の電話番号形式検証（+81形式）
- `ebs_size` の範囲チェック（10GB〜1000GB）
- `ebs_type` の有効性チェック（gp3, gp2, io1, io2）
- `timeout` の範囲チェック（60〜21600秒）
- 検証失敗時は処理を中断し、エラー通知を行います

### 3.3 EC2制御機能
**[004] EC2インスタンス起動**

定義ファイルに基づいてEC2インスタンスを起動します。

- デフォルトインスタンスタイプ：t3.micro（定義ファイルで変更可能）
- AMI：Amazon Linux 2（最新版）
- EBSルートボリューム：定義ファイルで指定（デフォルト20GB）
- EBSボリュームタイプ：定義ファイルで指定（デフォルトgp3）
- UserDataスクリプト：自律実行スクリプトを設定
- 起動後はLambdaから切り離され、自律実行します
- 起動失敗時はエラー通知を行います（リトライなし）

**[005] EC2自律実行**

EC2起動時にUserDataスクリプトが自動実行されます。

- S3からファイルダウンロード、シェル実行、結果アップロードを自律的に実行します
- 全処理完了後、自動的にインスタンスを停止します
- エラー発生時もインスタンスを停止し、課金を防ぎます
- 実行時間制限なし（長時間処理対応）

### 3.4 ファイル転送機能（EC2自律実行）
**[006] S3ファイルダウンロード**
- 入力バケット（${BKT_IN}）から実行シェルをダウンロードします
- 入力バケットから入力ファイルをEC2にダウンロードします

**[007] S3ファイルアップロード**
- EC2内で実行結果ファイルをS3にアップロードします
- ログファイルをS3にアップロードします

### 3.5 シェルスクリプト実行機能（EC2自律実行）
**[008] シェルスクリプト実行**

EC2上でBashシェルを使用してスクリプトを実行します。

- 実行権限を付与してから実行します
- 標準出力・標準エラー出力を全てキャプチャします
- 実行時間制限なし（長時間処理対応）

### 3.6 通知機能（EC2自律実行）
**[009] メール通知**

EC2内でSESを使用してメール通知を送信します。

- 送信者アドレス：定義ファイルの `ses_from_email` で指定
- 通知内容：処理完了、エラー発生

**[010] SMS通知**

EC2内でSNSを使用してSMS通知を送信します。

- 日本の携帯電話番号（+81形式）をサポートします
- 通知内容：処理完了、エラー発生

### 3.7 監視・ログ機能
**[011] ログ出力**

全処理過程をCloudWatch Logsに出力します。

- ログレベル：INFO, WARNING, ERROR, CRITICAL
- 日時、処理ID、実行内容を含めます

**[012] メトリクス収集**
- EC2インスタンスの使用状況を収集します（simple-act.log）

## 4. 非機能要件

### 4.1 性能要件
**[001] 処理性能**

- Lambda関数の起動時間：5秒以内
- Lambda関数の処理時間：5分以内
- EC2インスタンスの起動時間：3分以内
- ファイル転送速度：10MB/秒以上
- 通知送信時間：10秒以内
- シェルスクリプト実行時間：制限なし

**[002] 並列実行性能**

初期リリースでは、並列実行は行いません。

### 4.2 可用性要件
**[003] システム可用性**

- 単一AZ構成
- AWSの標準的なサービスレベルに準拠します。

**[004] 冗長化**

初期リリースでは、冗長化は行いません。

- 複数のAZ（アベイラビリティゾーン）を活用（次期以降のリリース）
- S3のクロスリージョンレプリケーション（次期以降のリリース）
- Lambda関数の自動スケーリング（次期以降のリリース）

### 4.3 セキュリティ要件
**[005] 認証・認可**

- IAMロールによる最小権限アクセス
- S3バケットポリシーによるアクセス制御
- EC2セキュリティグループによるネットワーク制御

**[006] 暗号化**
- S3データの暗号化（AES-256）
- 通信の暗号化（TLS 1.2以上）
- CloudWatch Logsの暗号化（次期以降のリリース）

**[007] 監査要件**
- 全AWS API呼び出しの記録（CloudTrail）
- アクセスログの保存期間：一ヶ月
- セキュリティイベントの即時通知

### 4.4 運用要件
**[008] 監視要件**

- 異常検知時の自動アラート

**[009] バックアップ要件**

- Lambda関数ソースコードのバックアップ（次期以降のリリース）
- 設定情報の定期バックアップ

**[010] 災害復旧要件**

- RTO（復旧時間目標）：24時間（次期以降のリリース）
- RPO（復旧時点目標）：1時間（次期以降のリリース）
- 災害復旧手順書の整備（次期以降のリリース）

## 5. 制約条件

### 5.1 技術的制約
- **プラットフォーム**: AWS のみ使用
- **リージョン**: 東京リージョン（ap-northeast-1）
- **Lambda制限**: 実行時間15分以内
- **EC2制限**: 実行時間6時間以内（timeout 最大値）

### 5.2 運用制約
- **通知制限**: SMS 1日100通まで

### 5.3 コスト制約
- **月額コスト上限**: $50
- **EC2インスタンス**: t3.microを基本とする
- **S3ストレージ**: 1TBまで

## 6. 前提条件

### 6.1 環境前提条件
- AWSアカウントが利用可能
- 必要なAWSサービスが有効化済み
- 管理者権限を持つIAMユーザーが存在
- Python 3.12以上の開発環境
- 単一AWSアカウントでの単一環境運用

### 6.2 運用前提条件
- システム管理者が運用手順を理解
- 基本的な障害対応手順が整備済み
- リソース命名規則の遵守（ts-プレフィックス統一）

### 6.3 データ前提条件
- 入力データは適切な形式で提供
- 実行シェルスクリプトは動作確認済み
- 機密データは事前に暗号化

## 7. 除外項目

### 7.1 機能除外項目
- Windows環境での実行
- リアルタイム処理機能
- GUI管理画面
- 外部システムとの連携

### 7.2 非機能除外項目
- 99.9%を超える可用性
- ミリ秒レベルの応答時間
- 大容量ファイル処理（10GB超）

- 統合テストが完了し成功している
- 性能要件を満たしている

### 8.2 品質受入れ条件
- 統合テスト成功率：100%
- セキュリティテスト完了

### 8.3 ドキュメント受入れ条件

## 9. 用語定義

| 用語 | 定義 |
|:-----|------|
| 定義ファイル | システムの実行内容を定義するJSONファイル |
| 実行シェル | EC2上で実行されるBashスクリプト |
| 入力ファイル | シェルスクリプトが処理するデータファイル |
| 結果ファイル | シェルスクリプトの実行結果を格納するファイル |
| ログファイル | シェルスクリプトの実行ログを格納するファイル |
| **管理者** | 本システムの運用・保守を担当する担当者。CloudWatchログの監視や異常発生時の一次対応を行う。 |
| **利用者** | 本システムを利用してバッチ処理を実行するユーザー。定義ファイルを作成し、S3にアップロードする操作を行う。 |

## 10. 付録

### 10.1 定義ファイルサンプル
```json
{
  "exec": "run.sh input.tar.gz",
  "log": "run.log",
  "result": "*.mp4 *act.log",
  "mail": "user@example.com",
  "sms": "+819012345678",
  "ec2_role_name": "ts-010-role-ec2-010",
  "subnet_name": "ts-010-subnet-010",
  "sg_name": "ts-010-sg-010",
  "ec2_instance_name_tag": "ts-010-ec2-010",
  "output_bucket": "${BKT_OUT}",
  "default_ami_id": "ami-09ed31f8f34719e20",
  "instance_type": "c6i.4xlarge",
  "ses_from_email": "sender@example.com",
  "prj_prefix": "ts-010",
  "ebs_size": 50
}
```

詳細は [設計書/定義ファイル仕様.md](定義ファイル仕様.md) を参照してください。

### 10.2 リソース命名規則
- S3バケット：${BKT_IN} / ${BKT_OUT}
- Lambda関数：ts-010-lmd-XXX
- EC2インスタンス：ts-010-ec2-XXX
- IAMロール：ts-010-role-XXX
- セキュリティグループ：ts-010-sg-XXX
